# BUO marketplace

BUO is a Nigerian-focused e-commerce MVP with a React + Vite frontend and Express API. The API uses PostgreSQL when `DATABASE_URL` is set; without it, the catalog and auth run in clearly limited in-memory demo mode. Gemini keys are used only by the backend.

## Stack

- Frontend: React + Vite + Tailwind
- Backend: Node.js + Express
- Database: PostgreSQL via `pg`, with numbered SQL migrations
- AI: Gemini REST API, grounded in matching PostgreSQL catalog rows
- Payments: DEMO only; Paystack is not yet integrated, so configuring a Paystack secret does not mark an order paid

## Local PostgreSQL + Gemini

1. Copy `.env.example` to `.env`.
2. Change `POSTGRES_PASSWORD` in `.env`, and set the same password (URL-encoded if needed) in `DATABASE_URL`.
3. Start PostgreSQL with Docker Compose:
   `docker compose up -d postgres`
4. Install dependencies:
   On Windows PowerShell, run `npm.cmd install` (use `npm install` in shells that do not block PowerShell scripts).
5. Create/update the database schema and load safe development data:
   `npm.cmd run db:migrate`
   Set `SEED_DEVELOPMENT_DATA=true` in local `.env`, then:
   `npm.cmd run db:seed`
6. Create a Gemini API key in Google AI Studio and set `GEMINI_API_KEY` in `.env`. The key is never sent to the browser.
7. Start the API and Vite frontend:
   `npm.cmd run dev`
8. Open `http://localhost:5173`; confirm the API/database state at `http://localhost:5000/health`.

The local development seed creates 13 categories, 30 products, a customer, an admin, and coupon records. Demo sign-in credentials are `ada@buo.ng` / `password123`; use only for local development. Seeding is idempotent, requires `SEED_DEVELOPMENT_DATA=true`, and always refuses to run when `NODE_ENV=production`.

## Database commands

- `npm.cmd run db:migrate` applies sorted, numbered files from `server/db/migrations` and records versions in `schema_migrations`.
- `npm.cmd run db:seed` inserts development records without resetting or overwriting existing product, user, or coupon rows. It requires the explicit local confirmation flag and will not run in production.
- The server checks PostgreSQL connectivity and refuses to start in database mode until migrations have been applied.

## Gemini behavior

The AI route requires both PostgreSQL and `GEMINI_API_KEY`. Gemini first extracts structured filters, the server queries PostgreSQL, and a second structured response may select only IDs from those matching rows. Returned product details, prices, stock, and specifications are loaded from PostgreSQL, not generated by Gemini. Without configuration the API returns an explicit unavailable response rather than fabricating recommendations. Requests are rate limited.

`GEMINI_MODEL` defaults to `gemini-2.5-flash`. `GEMINI_API_KEY` must remain a server-side environment variable.

## Production configuration

- Set `DATABASE_URL`, `JWT_SECRET`, `CLIENT_URL`, and `GEMINI_API_KEY` in the backend host's secret/environment settings.
- Set `DATABASE_SSL=true` when the PostgreSQL provider requires TLS.
- Run `npm run db:migrate` as a deployment/release step before starting the backend.
- Set `VITE_API_BASE_URL` to the public backend origin in the Vercel build environment; leave it blank for local Vite proxying. Build the frontend with `npm run build`.
- Never use the development seed on production data. No database credentials or third-party API secrets belong in the frontend environment.

## Container and Kubernetes validation

- Build the application image locally with `docker build -t buo:local .`.
- Run locally only after configuring the server environment: `docker run --rm -p 5000:5000 --env-file .env buo:local`.
- The image runs the Express API as a non-root user. `.dockerignore` excludes `.env` files from the image build context.
- `k8s/deployment.yaml` contains the application Deployment and ClusterIP Service. Create the `buo-secrets` Kubernetes Secret out of band with `database-url` and `jwt-secret`; add `gemini-api-key` to enable Gemini. Do not commit secret values.
- The Kubernetes image reference is a placeholder until BUO publishes an image to a registry. The GitHub Actions workflow currently checks lint/build, builds the image without publishing it, and validates the Kubernetes manifests; it does not deploy to a cluster.
- Every push or pull request targeting `main` runs `.github/workflows/ci.yml`. A successful run should show lint/build, Docker image build, and Kubernetes schema validation.
